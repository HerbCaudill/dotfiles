# Primary DevResults startup on mini

This directory owns the managed replacement for the previously unmanaged `C:\Users\herb\setup\start-site.ps1` task action. The legacy repository's `scripts\Start-Azurite.ps1` remains untouched. `start-site.ts` runs directly with an explicitly installed Node 24 executable; it has no package-manager, download, install, or build step.

The configuration lists installed Node/Azurite entrypoint pairs in preference order. Each pair must pass a bounded offline `--version` command with the expected version. Missing, incomplete, stalled, or wrong-version installations are rejected with a clear error. The default verification and readiness bounds are each two minutes because a cold installed Azurite CLI on mini exceeded five seconds. Provisioning a complete installation is a separate operator action. The example records the already-installed executable used by the October 28 recovery; its npm-cache path can be pruned, so verify it again at handoff or configure another separately provisioned installation. Startup never searches caches or resolves a package.

Before starting anything, the supervisor refuses occupied primary ports. It never adopts or stops an existing listener. It requires the existing primary data directory, starts Azurite directly, and checks the Blob, Queue, and Table HTTP response identities on loopback. Only then does it launch IIS directly. It keeps checking storage and both child lifetimes. Dependency loss or either child exiting fails the task, stops only this invocation's children, and retains diagnostics. This is process and storage supervision; application HTTP health still needs a separate check.

`status.json`, `Azurite.log`, and `IIS.log` are written under the configured log directory. The status distinguishes starting, storage-ready, running, stopped, and failed and includes child PIDs. A failed launch exits nonzero. The installer registers an unlimited-duration limited-S4U `DevResults site` task one minute after boot, with duplicate invocations ignored. It copies the supervisor and explicit configuration into a new release directory, refuses an existing release, and does not start the task. Future source updates therefore do not rewrite files that a running release uses.

## Deployment boundary

**This source has not been deployed to primary.** The recovered IIS and triggerless `DevResults primary Azurite recovery` task remain running. Their scripts, scheduled-task definitions, executable installation, blob data, and debug paths were preserved. The primary data remains `C:\Code\DevResults\devresults\DevResults\.azurite\data`; the debug log remains `C:\Code\DevResults\devresults\DevResults\azurite_debug.log`.

A live handoff requires a coordinated maintenance window with the photo/runtime owner. The installer deliberately refuses while the primary task is running or any primary port is listening. During that future window, record exact IIS/recovery identities, stop only the coordinated primary writers, confirm ports 8443 and 10000–10002 are free, and run `pwsh -NoProfile -File install-primary-site.ps1 -ConfigPath <reviewed-primary.json> -ReleaseName <commit>`. Start `DevResults site` only after the old recovery owner has yielded the ports. Check dependency status, read-only API health, and the owned-contact photo workflow before retiring the transient recovery task. Do not change data paths, copy live storage, restart any private/e2e lane, or edit open runtime files. If handoff fails, retain logs and coordinate restoration of the original task action and unchanged recovery; never run two storage writers on the primary directory.

The tests use real child processes and fresh loopback ports to cover readiness ordering, bounded missing/stalled/wrong-version executable failures, storage exit, IIS exit, cleanup, and occupied-port refusal.
