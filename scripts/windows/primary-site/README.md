# Primary DevResults startup on mini

This directory owns the managed replacement for the previously unmanaged `C:\Users\herb\setup\start-site.ps1` task action. The legacy repository's `scripts\Start-Azurite.ps1` remains untouched. `start-site.ts` runs directly with an explicitly installed Node 24 executable; it has no package-manager, download, install, or build step.

The configuration lists installed Node/Azurite entrypoint pairs in preference order. Each pair must pass a bounded offline `--version` command with the expected version. Missing, incomplete, stalled, or wrong-version installations are rejected with a clear error. The default verification and readiness bounds are each two minutes because a cold installed Azurite CLI on mini exceeded five seconds. Provisioning a complete installation is a separate operator action. The example records the already-installed executable used by the October 28 recovery; its npm-cache path can be pruned, so verify it again at handoff or configure another separately provisioned installation. Startup never searches caches or resolves a package.

Before starting anything, the supervisor refuses occupied primary ports. It never adopts or stops an existing listener. It requires the existing primary data directory, starts Azurite directly, and checks the Blob, Queue, and Table HTTP response identities on loopback. Only then does it launch IIS directly. It keeps checking storage and both child lifetimes. Either child exiting fails the task at once. Storage that stops answering fails it only after it stays unresponsive for `storageGraceMs` (default 60 seconds), with each probe allowed `probeTimeoutMs` (default 5 seconds). A failure stops only this invocation's children and retains diagnostics. This is process and storage supervision; application HTTP health still needs a separate check.

`status.json`, `status.log`, `Azurite.log`, and `IIS.log` are written under the configured log directory. The status distinguishes starting, storage-ready, running, storage-degraded, stopped, and failed and includes child PIDs. `status.json` holds the latest state; `status.log` appends every state as a JSON line, so the reason for a failure survives the next start. A failed launch exits nonzero. The installer registers an unlimited-duration limited-S4U `DevResults site` task one minute after boot, with duplicate invocations ignored. It copies the supervisor and explicit configuration into a new release directory, refuses an existing release, and does not start the task. Future source updates therefore do not rewrite files that a running release uses.

## Deployment

Deployed to the mini on 2026-11-17 as release `64edb2b`, in `%LOCALAPPDATA%\devresults-site\releases\64edb2b`. The reviewed configuration is `C:\Users\herb\setup\primary-site\primary.json`. Its first candidate is a dedicated Azurite 3.37.0 install in `C:\Users\herb\setup\primary-site\azurite-3.37.0`, made with `npm install --prefix`; the npm-cache copy from October stays as a fallback. The data and debug paths are unchanged.

Before the handoff, the old task's `pnpm dlx` Azurite launcher had hung since the 15 November reboot, so the primary data folder had no Azurite. A separate `azurite-blob` started by hand on 16 November, with data in `C:\Users\herb\.local\state\azurite-next`, held port 10000, and the site used it. Its `development` container was copied into the primary data folder before it was stopped. That folder is left on disk. The triggerless `DevResults primary Azurite recovery` task is disabled, so it can't start a second writer on the primary data folder.

Release `64edb2b` stopped the site whenever one storage probe took longer than 500 ms. On the busy mini, Azurite stalls of 0.6–6 seconds took the site down three times on 2026-11-17, and each restart overwrote the failure reason in `status.json`. The grace window and `status.log` replaced that behavior in the following release.

The task runs with limited rights, so IIS Express needs a URL reservation for its HTTPS binding: `netsh http add urlacl url=https://127.0.0.1:8443/ user=herb listen=yes`, which is in place on the mini.

To restart the site, stop the `DevResults site` task, then end the Azurite and IIS PIDs listed in `status.json`. Stopping the task ends the supervisor without letting it stop its children, and the next start refuses ports that are still held. The handoff was checked with a task start, not a reboot.

## Verification

Run `pnpm exec vitest run scripts/windows/primary-site/tests/supervisePrimarySite.test.ts` from dotfiles. The tests use real child processes and fresh loopback ports to cover readiness ordering, bounded missing/stalled/wrong-version executable failures, storage exit, IIS exit, cleanup, and occupied-port refusal. They need only existing repository dependencies.

On Windows, run `pwsh -NoProfile -File tests/install-primary-site.tests.ps1` to parse the installer and test deployment guards with command stubs. It never changes real scheduled tasks or listeners. Run `node tests/verifyInstalledFixture.ts <installed-node.exe> <installed-azurite.js>` from a disposable source copy for an actual installed-Azurite smoke check. It creates a new temporary directory and fresh OS-assigned ports, uses a disposable Node app in place of IIS, verifies all three real services, stops only its own children, and retains fixture diagnostics. No existing primary/private/e2e storage is read or changed by that fixture.

No primary runtime handoff or reboot proof has been performed.
